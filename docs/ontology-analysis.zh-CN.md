# OntoKB 知识图谱本体重构与选型分析报告

日期：2026-09-26

研究对象：当前 OntoKB 本地知识库（两条已入库内容、63 个节点、90 条关系）

选用模型：**Schema.org 的研究知识库应用剖面 v2**

实施状态：已迁移本机数据库，已更新抽取规则、校验、Obsidian 投影与交互图谱。

## 1. 结论与选型边界

建议以 Schema.org 作为这套互联网研究知识库的公共语义骨架，用受控子集限制分类自由度，再补充少量明确标注的本地关系。此次已经按这个方案实施。

需要准确区分：Schema.org 是成熟的互联网结构化数据词汇及数据模型，**不是覆盖世界全部知识的严格通用 OWL 本体**。官方明确表示，它不以“全球通用本体”为目标，而且类型和属性约束具有较强的实用、开放特征。本项目采用的是应用剖面：从中选定一组类型，附加本地强校验，而非原样导入整套词汇。[Schema.org 数据模型](https://schema.org/docs/datamodel.html)

这个选择针对当前数据的性质：资料以视频和文章为入口，内容围绕公司、人物、软件、技术概念，以及采访者的判断和预测。相比覆盖大量百科细类，当前更需要把“对象是什么”“资料讨论什么”“谁提出了什么说法”分清。

这次重构解决分类与入库一致性问题，并保留现有语义证据。没有重新让语言模型改写全部事实，也没有把全部旧关系重新事实核查。“迁移校验通过”仅表示结构满足本项目规则。

## 2. 现状诊断：为什么原来的图谱显得乱

以下观察来自迁移前 SQLite 快照、现有程序和缓存转录，不是对所有知识图谱的泛泛评价。

| 问题 | 当前实例或代码行为 | 造成的后果 | 此次处理 |
|---|---|---|---|
| 把对象类型与主题角色混在一起 | `Technology` 与 `Topic` 并列，Transformer 是技术，自动驾驶是话题 | 同一概念可能因抽取方式不同获得不同类型 | 抽象概念统一为 `DefinedTerm`；“被讨论”由 `about` 表达 |
| 内容类型过粗 | 两个 YouTube 视频和《技术革命与金融资本》都为 `Content` | 无法按资料媒介可靠筛选 | 分别映射为 `VideoObject` 和 `Book` |
| 具体产品和技术原理混杂 | FSD 与 Transformer 同为 `Technology` | 软件实例与技术类别混同 | FSD 为 `SoftwareApplication`，Transformer 为 `DefinedTerm` |
| 无法判断的对象没有解释 | River 为 `Thing`，仅保存“标题描述：AI 员工” | “其他”像无规则垃圾桶 | 保留对象并标记待复核，记录缺证原因 |
| 关系校验与落库类型可能不一致 | 三元组可优先用当前抽取批次的类型，但实体合并保留旧类型 | 临时类型能掩盖持久化类型冲突 | 所有关系按实际数据库类型校验 |
| 别名冲突被静默忽略 | 别名表 `INSERT OR IGNORE`，实体 JSON 仍可能记录同一别名 | 不同查询路径对同一别名可能给出不同归属 | 写入前拒绝跨实体别名占用；迁移预检已有别名一致性 |
| 缺少公共语义标识 | `worksAt`、`Content` 等主要是项目自定义名字 | 对外交换时语义需要重新解释 | 类型使用 Schema.org URI，关系明确区分官方词汇与本地扩展 |
| 资料边占据大部分画面 | `about` 17 条、`mentions` 44 条，合计 61/90（67.8%） | 资料节点形成中心辐射，掩盖对象之间的少量知识关系 | 默认实体／概念视图，另设论断、资料、全部视图 |

原库不是所有分类都错误：17 个组织、3 个人物、19 条论断基本具备可用的上层类型。此次保留这些身份与证据，仅细化或规范需要调整的部分。

另一个需要正视的问题是数据量和关系密度。剥离资料与论断后，当前实体／概念之间只有 9 条关系。画面出现孤立节点，并不意味着新模型失败；它说明这些对象目前仅被资料提及，库里还没有足够的对象间关系。不能为了画面好看而凭空补边。

## 3. 经典模型比较

下表是基于本项目使用场景的工程判断，不是权威排名，也不是性能基准测试。

| 方案 | 主要定位 | 对本项目的优势 | 主要代价 | 本次决定 |
|---|---|---|---|---|
| **Schema.org** | 互联网实体、作品、产品等的共享结构化词汇 | 人物、组织、软件、视频、文章、书籍、论断都有可复用类型；易与网页资料对应 | 本身约束宽松；科技研究关系需本地扩展 | **选为主体，收窄成可执行应用剖面** |
| **DBpedia Ontology** | 将 Wikipedia 不一致的信息框映射到统一跨领域本体 | 适合百科实体和外部知识链接，分类细致，来源成熟 | 对当前两条资料而言，完整分类范围过大；仍需补研究论断与来源建模 | 作为未来百科实体对齐目标，不整体搬入 |
| **Wikidata 数据模型** | 项目、属性、陈述、限定符、参考资料和等级 | 擅长一个说法的来源、时间限定和多个相互冲突的值 | 陈述中心模型会增加存储、查询和界面复杂度；直接复制不能自动解决分类规则 | 借鉴来源意识，后续有时态需求再引入更完整陈述层 |
| **SKOS** | 概念词表、分类表、主题词及其标签关系 | 适合多语言术语、上下位概念、主题体系 | 单独使用不能覆盖人物、产品、文档、论断的全部身份建模 | 以后术语层需要上下位关系时再扩展，目前不引入第二套概念类型 |

DBpedia 的官方介绍说明，其本体用于归一化信息框中不一致的类别、属性和数据类型；这正是一个经典互联网知识库本体，但它的百科建模出发点与本项目的资料研究出发点不同。[DBpedia Ontology](https://www.dbpedia.org/resources/ontology/)

Wikidata 的陈述允许附加限定符、参考资料与等级，适合表达“何时、在何种条件下、根据谁”。这是未来处理职位变更、模型版本、预测期限的参考，而非此次已实现的能力。[Wikidata Statements](https://www.wikidata.org/wiki/Help:Statements)

SKOS 面向知识组织系统中的概念与标签，并提供 `broader`、`narrower`、`related` 等关系。若将来需要正式维护“人工智能 → 机器学习 → 大模型”的主题词表，它会比不断新增业务实体类型更合适。[W3C SKOS Primer](https://www.w3.org/TR/skos-primer/)

## 4. 新模型：类型、主题角色与论断分开

### 4.1 受控类型树

本项目的类型注册表包含 13 个类，其中有些是必要父类，并非鼓励每次抽取都直接使用。所有类使用 Schema.org 的正式 URI。下图是选定子集，不是 Schema.org 完整继承树。

```text
Thing                         未分类对象；具体实例仅作待复核兜底
├─ Person                     自然人
├─ Organization               组织
├─ Product                    具体产品
├─ DefinedTerm                概念、术语、研究主题
├─ Event                      具体事件
└─ CreativeWork               作品
   ├─ MediaObject
   │  └─ VideoObject          视频
   ├─ Article                 文章
   ├─ Book                    书籍
   ├─ SoftwareApplication     软件应用
   └─ Claim                   论断、判断、预测
```

`SoftwareApplication` 继承 `CreativeWork`，不是为了 UI 方便而被错误挂到 `Product` 下面。界面将它显示在实体层，是展示策略，不改变类型继承。[SoftwareApplication 官方类型](https://schema.org/SoftwareApplication)

`DefinedTerm` 用于有可复用名称的术语或概念；本地 `termCategory` 可保留“技术／研究主题”的原始分类线索，但不再建立两个互斥顶层类别。未来有需要时，可进一步补描述与所属术语集。[DefinedTerm 官方类型](https://schema.org/DefinedTerm)

`Claim` 本身是作品的一种。把一个判断保存为 Claim，并不意味着认定它为真，也不等同于完成 ClaimReview。[Claim 官方类型](https://schema.org/Claim)

### 4.2 分类决策规则

| 判断步骤 | 应使用的类型或关系 | 例子 |
|---|---|---|
| 是一个有身份的自然人吗？ | Person | 王宇权、Tobi Lütke |
| 是一个机构吗？ | Organization | OpenAI、Shopify |
| 是命名的软件应用，而非通用原理吗？ | SoftwareApplication | FSD |
| 是具体产品吗？ | Product；本剖面软件优先归软件类 | 某款具体硬件，而非“AI 芯片”这个类别 |
| 是被引用或采集的具体作品吗？ | 按媒介选 VideoObject／Article／Book | 《技术革命与金融资本》 |
| 是完整、可被支持或反驳的句子吗？ | Claim | “2029 年前后可能出现科技投资泡沫” |
| 是可反复讨论的概念或研究领域吗？ | DefinedTerm | Transformer、自动驾驶、AI 芯片 |
| 仅知道名字，无法判断身份吗？ | Thing + needs_review | River |
| 某资料讨论了一家公司吗？ | 资料 `about` 公司 | 公司仍是 Organization，不能重分为 DefinedTerm |

“研究主题”是资料与对象之间的关系角色，不必成为对象身份。例如一篇文章关于 OpenAI，那么 `Article → about → OpenAI` 就足够，不需要另造一个名为 OpenAI 的话题节点。`about` 的对象在标准中可以是 Thing，并不局限于主题词。[Schema.org about](https://schema.org/about)

### 4.3 关系词汇与扩展边界

| 关系 | 方向与用途 | 词汇来源 |
|---|---|---|
| mentions | 作品 → 被提及对象 | Schema.org |
| about | 作品／论断 → 讨论对象 | Schema.org |
| author | 作品／论断 → 人物或组织作者 | Schema.org |
| publisher | 作品 → 人物或组织发布者 | Schema.org |
| worksFor | 人物 → 组织 | Schema.org |
| citation | 作品 → 被引用作品；本剖面只接受节点 | Schema.org 的收窄用法 |
| develops、adopts、makes、uses | 开发、采用、制造、使用 | 本地扩展 |
| makesClaim | 说话者或来源 → 论断 | 本地扩展 |
| supports、contradicts | 论断 → 论断 | 本地扩展 |
| competesWith、relatedTo | 竞争、一般关联 | 本地扩展 |
| participatesIn、doesNotParticipateIn | 人物／组织 → 事件 | 本地扩展 |

标准关系使用 `https://schema.org/…`；本地扩展使用 `urn:ontokb:ontology:…`。没有把 `develops`、`makesClaim` 等包装成标准官方属性，也没有把方向相反的 `makes` 硬映射为 `manufacturer`。

旧 `worksAt` 规范为 `worksFor`；旧 `authoredBy`、`publishedBy` 作为输入兼容别名，规范为 `author`、`publisher`。作者可以是人物或组织，不能因为人物出现在视频中，就自动认定其为视频作者。[worksFor](https://schema.org/worksFor)、[author](https://schema.org/author)

每条本地关系都有显式 domain/range；联合范围解决了“开发对象可能是软件、产品或技术概念”的实际需求。对称标记保留在模型中，但当前存储不会自动补反向三元组，也没有完整推理机。

## 5. 优点：对这套知识库具体有什么帮助

### 5.1 分类有稳定公共参照，减少自由造类

以前的抽取输出只有简短类型列表，模型容易根据措辞选择 Topic、Technology 或 Thing。现在有正式 URI、中文定义、正反边界和最具体类型原则，抽取与迁移使用同一份配置。新增领域首先成为一个术语实例，而不是随意扩展顶层类。

这能降低分类漂移，但不能保证模型永远判断正确。确定的收益是：输出范围受控、冲突可检出、相同规则可复现；分类准确率提升仍需要标注集测量。

### 5.2 媒介、对象和观点可以独立检索

资料媒介对应 VideoObject／Article／Book；人物和机构保持现实对象身份；完整判断归 Claim。因此能分别问“哪些资料讨论自动驾驶”“哪个组织开发某软件”“谁提出这项预测”。三个问题不再依赖混杂类型去猜。

视频、书籍均沿着 CreativeWork 父类复用作品关系。增加文章资料时，不需要再写一套与视频完全分离的图谱。[VideoObject](https://schema.org/VideoObject)、[Book](https://schema.org/Book)

### 5.3 与互联网结构化资料更容易交换

正式类型和属性 URI 为以后接入网页 JSON-LD、外部实体库或语义工具提供公共语言。此次还交付 JSON-LD 1.1 导出，每个节点携带类型 URI，每条关系以带来源和证据的 RDF Statement 输出。

导出的陈述不直接宣告为无条件事实；置信度、出处和证据仍然存在。本地实体 URI 采用数据库 ID，适合此库快照交换；它不是全网实体身份，需要跨库合并时仍必须做实体对齐。

### 5.4 迁移成本可控，可回溯

当前规模不需要立即换成图数据库服务器。SQLite 保留已有实体编号和三元组编号，映射仅调整类型、关系名和分类元数据。无需重新下载、重新转录或调用付费模型；审查者可以对照迁移报告逐个核对。

### 5.5 可以把结构错误拦在入口

现在按持久化类型校验边，拒绝无效的跨类型合并和别名冲突，允许有依据的父类向子类细化。新类型若使已有关系失效，也会被拒绝。相比只在展示层换颜色，这改善了后续数据的一致性。

## 6. 缺点、风险与已经采用的补偿

| 局限 | 对本项目的影响 | 当前补偿 | 尚未解决的部分 |
|---|---|---|---|
| 标准本身约束宽松 | 单纯“采用 Schema.org”仍可能生成混乱数据 | 本地限定类表、关系表、继承和端点类型 | 尚无完整 SHACL 形状、属性基数和全部字段数据类型校验 |
| 不是专门的科技研发本体 | 研发、采用、竞争、论证关系不够直接 | 11 个本地关系，使用独立 URN 命名空间 | 外部系统需要读取项目映射，不能自动理解全部扩展语义 |
| DefinedTerm 覆盖面较宽 | 技术原理、能力、主题和类别仍集中在一层 | 固定定义，保留原分类线索作为属性 | 暂未建立经审定的上下位术语体系 |
| 标准允许更丰富的多类型、多继承 | 软件也可能在商业语境下被作为产品 | 当前明确选择一个主类型；软件优先 SoftwareApplication | 未实现同一实体多个 rdf:type，不能宣称完全覆盖标准能力 |
| 分类不等于消歧 | 同名公司、产品、自然人仍可能误撞 | 不兼容类型拒绝、别名冲突拒绝 | 同类型同名对象仍依赖全局名称键，尚无权威 ID 驱动消歧 |
| Claim 不等于事实核查 | 预测或意见可能被误认为知识事实 | 标记 unverified，保留来源，页面单独展示 | 未核验断言真实性、时间有效性或来源可信度 |
| 缺乏完整限定符与时态 | 职位、版本、预测期限等难以精细查询 | 保留原文证据与已有时间字段 | `added_time` 是入库时间，不是事实有效期；未实现 Wikidata 式限定符 |
| 存储与导出仍是轻量实现 | 无法直接宣称具备 SPARQL／OWL 推理 | SQLite 查询与 JSON-LD 导出 | 没有 RDF 三元组服务、OWL 推理或外部实体自动链接 |
| 标准会演进 | 后续升级可能产生兼容成本 | 记录本地 profile version=2、查阅日期和确定 URI | 没有锁定完整官方发行包；升级需人工审查映射 |

尤其要避免两个误解：第一，`Thing` 不是必须清零的坏类型。当证据不足时保留待复核，比强行归到“软件”更诚实。第二，闭世界校验是本项目的工程约束；它不是 Schema.org 官方对所有使用者的强制规则。

## 7. 已有数据的迁移结果

### 7.1 类型分布

| 旧类型 | 迁移前 | 新类型去向 |
|---|---:|---|
| Organization | 17 | Organization 17 |
| Person | 3 | Person 3 |
| Topic | 17 | DefinedTerm 17 |
| Technology | 3 | DefinedTerm 2；SoftwareApplication 1 |
| Content | 3 | VideoObject 2；Book 1 |
| Claim | 19 | Claim 19，补 text 与 unverified 标记 |
| Thing | 1 | Thing 1，明确待复核 |
| **合计** | **63** | **63，未删除、未猜测合并** |

迁移实际改变 **23 个实体的类型**，规范 **2 条 worksAt 关系为 worksFor**。所有 90 条关系均保留；2 条 contents 原始记录均保留。类型和关系约束错误为 0。所有实体补入对应的公共类型 URI 和本地版本标记。

### 7.2 人工审查过的特殊映射

1. **FSD → SoftwareApplication**：转录讨论装有 FSD 的特斯拉及其驾驶能力，可将其辨识为具体软件系统。映射理由写在 `ontology/migration-v2.yaml`。这里做的是类别判定，不是核实视频对其能力的评价。
2. **《技术革命与金融资本》→ Book**：转录明确称它为一本书，旧属性也标明“访谈中引用的书籍”。
3. **River → Thing／待复核**：现有库仅有视频标题级的“AI 员工”描述，不足以确认身份。没有凭名字去绑定网上某个同名产品。

`Transformer` 与“开源大模型”映射为 DefinedTerm：前者在现有语境是架构概念，后者是模型类别，而不是一个有明确版本和身份的具体模型产品。

### 7.3 未经重新核验的旧关系

两条旧就业关系仍保留：其证据分别是“海银资本创始人”和马斯克以“我们”讨论特斯拉。它们可以支持某种组织关联，但并不完整描述任职性质、时间和法律雇佣关系。此次只规范名称，没有把其证据质量判为合格。

类似地，“某公司 develops 开源大模型”保留的是原始概括性陈述；将来应在来源有依据时细化到具体模型及版本。将其映射到 DefinedTerm 不意味着相关概念是该公司的独占发明。

缓存转录含有 OpenEye、Wemo 等识别变体，说明源文本本身也需要质量管理。更换本体不能修复听写错误。建议以后把“转录校正”和“事实核验”作为独立流程，而不是在分类迁移中静默改写证据。

## 8. 程序与界面具体变化

| 部分 | 已实现行为 |

## 11. 后续治理建议

先处理质量，再增加分类颗粒度。第一优先级是确认 River 的实际身份、检查旧任职关系的语义和时间、建立小型人工审定样本。遇到证据不足的节点，不以猜测消除“待复核”。

第二优先级是实体身份管理：当同名对象增多时，从当前全局名称键升级为稳定 ID、来源内别名、候选归并和显式审核。此问题无法仅靠换本体解决。

第三优先级才是主题上下位体系和时间限定陈述。若术语复用规模明显增长，可引入 SKOS 对齐；若大量问题涉及“何时担任”“哪个版本”“预测期限”，再扩展成带限定符的陈述模型。现在直接搬入大型百科本体或完整推理系统，会增加维护成本而不能优先修复最主要的数据问题。

新增类型或关系应在同一次修改中给出定义、例子、排除条件、公共 URI 或本地命名空间、迁移方式和验证测试。避免再次回到“遇到新词就造新类”的状态。
